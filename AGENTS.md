# Development

This repository (nanocodexyz/egress, MIT or Apache-2.0) is `nanocode-egress`, an extension of gakonst/nanocode-ts that runs nanocode agents on a user's own ChatGPT or Claude plan on Cloudflare Workers and Vercel: it signs the user in, keeps the plan's OAuth credential sealed and owned in one place, and injects it into the session's model requests at the egress, so the agent's runtime never holds it. It follows nanocode-ts's TypeScript conventions (namespace modules, `.ts` imports, factories rather than classes except Durable Objects, option bags, TSDoc on exports). Check with `npm run check:types` and `npm test` (`node --test` over `test/*.test.ts`, with mocked OAuth and provider endpoints), and `npm run build` writes `dist/`, which `prepare` builds when the package is installed from Git.

nanocode-ts wraps this package so a deployment writes no plan code (gakonst/nanocode-ts#169, #171 and #172, from `build-a9ab16b` on): `App.create({ plans: { vault, relay, account } })` on Cloudflare and `App.create({ account, plans })` on Vercel build the binding, vault, `subscription` and sign-in routes from the pieces below, `PlanVault` and `RelayContainer` are re-exported from `nanocode-ts/cloudflare`, and `nanocode-ts/client`'s `Plans.create` and `Plans.serves` and `nanocode-ts/react`'s `usePlans` and `PlanConnect` are the browser side. A plan serves only its vendor's models (Anthropic's `claude-` and OpenAI's `gpt-` ones), so nanocode-ts keeps other models of a signed-in provider on the deployment's gateway. On 2026-10-28 gakonst/nanocode-cloudflare-durable (`284a50e`, nanocode.xyz/cloudflare, with the relay container) and gakonst/nanocode-vercel-durable (`edd9212`, nanocode.xyz/vercel) shipped visitor sign-in this way; both refuse a request without the visitor's identifier with 401, and `/plans` answered a new visitor with both plans `signed_out`.

## Library

- `ChatGpt` and `Claude` port the nanocode SDK's `ChatGptSubscription` (crates/backends/codex/client/src/auth/subscription.rs) and `ClaudeSubscription` (crates/backends/claude/client/src/subscription.rs) with the same endpoints, OAuth clients, scopes, stored JSON and refresh rules: ChatGPT's device authorization at auth.openai.com (`start` returns the code for `/codex/device`, `status` polls after the interval, refreshes single-flight per generation, a stale rejection does not refresh twice), and Claude's PKCE authorization at claude.com with Anthropic's manual code page (`start`, `complete` with the pasted `code#state` or the callback URL, profile validation, account on hold, refreshes that keep the account and organization, `reject` after a 401, sign-out that revokes the refresh token). Claude's envelope binding is the SHA-256 of the configuration in the SDK's field order, so state is interchangeable with the SDK's.
- `Store` is the host contract (per-key compare-and-swap over `{ revision, payload }`, `Store.memory()` for tests), `Vault` seals payloads with AES-256-GCM under an HKDF key from a deployment secret of at least 32 characters, bound to the store key (`Vault.sealed(store, vault)`), and `Plans.account(store, { account })` is one account's two plans behind `Plans.Account`: `status`, `signedIn`, `signIn`, `complete`, `signOut`, `inject(provider)` (the credential headers and the generation a rejection names) and `rejected`.
- `Egress` serves only the plans' endpoints (`https://api.anthropic.com/v1/messages` and `/count_tokens` with `?beta=true`, `https://chatgpt.com/backend-api/codex/responses` and `/compact`), drops the request's own credentials, cookies and hop-by-hop headers, injects the plan's (Claude: `authorization` and the `oauth-2025-04-20` beta merged into `anthropic-beta`; ChatGPT: `authorization`, `chatgpt-account-id` and `x-openai-fedramp`), refuses redirects, and retries a request once with a refreshed credential after a 401. It also drops the request's `accept-encoding`, so the runtime's `fetch` asks only for encodings it decodes (undici `br, gzip, deflate`, Workers gzip and br), and removes `content-encoding`, `content-length` and `transfer-encoding` from a response whose coding is one of those, because `fetch` hands over the decoded body with the original headers: Anthropic gzips its event streams, and a Vercel function that returned such a response sent its client an empty 200 (chatgpt.com does not compress, and Workers re-encode, so only Claude on Vercel showed it). `Egress.socket` gives the URL and headers of a Codex WebSocket, which nanocode-ts's WASM opens for every ChatGPT-plan session.
- `Routes.handle` serves the sign-in API for the account a host authenticated: `GET /plans`, `POST /plans/{claude|codex}/sign-in`, `POST /plans/claude/complete` with `{ code }` and `DELETE /plans/{claude|codex}`.

## Cloudflare (`nanocode-egress/cloudflare`)

A `PlanVault` Durable Object per account (`idFromName(account)`) owns that account's plans in its SQLite storage, sealed with `PLAN_SECRET`; one object per account makes refreshes single-flight. nanocode-ts's Cloudflare `App.create` already sends every model request to its `egress` binding with `subscription` in the dispatch, so a deployment wires it as:

```ts
const plans = Egress.durable<Env>((env) => env.PLANS)
App.create({
  egress: Egress.binding({ plans, fallback: (env) => Gateway.create(env.AI, { id: env.AI_GATEWAY_ID }) }),
  subscription: Egress.subscription({ plans }),
})
```

`binding` answers `/model` dispatches with `subscription` from the account's plan and `/socket` (Codex) by opening `chatgpt.com` with the plan's headers, and forwards everything else to `fallback`. chatgpt.com's edge answers HTTP 403 (its HTML "blocked" page) to every request that carries the `cf-worker` header, which workerd adds to each subrequest and a Worker cannot remove, over HTTPS and WebSocket alike, while it serves the same request from Node and Anthropic serves Workers directly; so ChatGPT plans on Workers need `binding`'s `relay(env)`, such as `Egress.relay({ url, secret, fetcher })`, which sends Codex requests and sockets to a `nanocode-egress/relay` server with `x-nanocode-relay-secret`. The relay (`Relay.create({ secret })`, or the `nanocode-egress-relay` binary with `RELAY_SECRET` and `PORT`) is a Node server for a Cloudflare Container or any Node host: it forwards only POSTs and WebSocket upgrades of `/backend-api/codex/responses` and `/compact` without a query to `https://chatgpt.com`, refuses a missing or wrong secret (at least 32 characters) with 401 and other paths with 403, and drops its secret, hop-by-hop, `cf-*` and `cdn-loop` headers. Before it dropped `cf-*`, relayed requests still got 403, because Node forwarded the Worker's `cf-worker`. `nanocode-egress/cloudflare/container` runs the relay in a Cloudflare Container (`@cloudflare/containers`, an optional peer dependency) and needs nothing but `PLAN_SECRET`: `RelayContainer` listens on 8080 with a relay secret it derives from `PLAN_SECRET` (HKDF-SHA-256, info `relay secret v1`, apart from the vault's key) before it starts and sleeps 10 minutes after its last request, and `relay(env.RELAY, { secret: env.PLAN_SECRET })` is the `relay` option, deriving the same secret and reaching the container through its stub's `fetch`, which forwards WebSockets too. Its image is `relay.Dockerfile` in the installed package (Node 24 with undici and ws, running `dist/relay/main.js`), so a deployment's `wrangler.jsonc` names `"image": "./node_modules/nanocode-egress/relay.Dockerfile"` and no build context: wrangler builds in the Dockerfile's directory, which `relay.Dockerfile.dockerignore` limits to the relay's two files. A binding without `relay` answers every ChatGPT-plan request and socket with 503 and a message naming this setup instead of sending it to chatgpt.com's 403 page, and a container that does not answer fails with a message naming `containers`, `durable_objects` and `wrangler deploy`. On 2026-10-28 `docker build -f node_modules/nanocode-egress/relay.Dockerfile node_modules/nanocode-egress` built the image in the example, and the container answered 401 without the secret and passed a request with it to chatgpt.com. `Egress.routes({ plans, account })` serves the sign-in API, where `account(request, env)` must name the same account as `App.create`'s `authenticate`. `examples/cloudflare` is a Worker with the vault, the relay container, nanocode sessions (`App.create({ authenticate, egress, subscription: Egress.subscription({ plans }) })` from nanocode-ts's `build-6cbf34b` release, serving `/sessions/*` with the `AgentSession` Durable Object of migration v2 and the runtime variables in `wrangler.jsonc`), the routes, a `/probe` route that sends one model request through the binding and a `/probe-socket` route that sends one Codex WebSocket message through it; `RELAY_URL` replaces the container with a relay elsewhere. Every route requires `authorization: Bearer <DEMO_TOKEN>` (at least 32 characters; without it the Worker refuses everything) and serves the account `x-demo-account` names, `demo` by default, standing in for a host's own login. `npm run build` there bundles it with Wrangler (13 KiB gzipped on 2026-10-28). To deploy it, put `PLAN_SECRET` and `DEMO_TOKEN` in a JSON file outside the repository and run `npx wrangler deploy --secrets-file <file> --containers-rollout immediate` with Docker running, which builds the linux/amd64 image and pushes it to Cloudflare's registry; the account needs Containers, which come with Workers Paid.

## Vercel (`nanocode-egress/vercel`)

`Redis.store()` keeps the records in Upstash Redis over its REST API (`KV_REST_API_URL` and `KV_REST_API_TOKEN`, as a Vercel Marketplace Redis database sets them), swapping with a Lua script, and `Egress.plans({ store })` seals them with `PLAN_SECRET`. nanocode-ts's Vercel adapter takes a plan per session through `App.create`'s `account(request)` and `subscription` (gakonst/nanocode-ts#167, merged 2026-10-28 and released from `build-1bffe70` on): `Egress.subscription(plans)` returns the account's plan while it is signed in, with `dispatch` and, for Codex, a `socket` over undici's WebSocket (an optional peer dependency, since Node's global WebSocket takes no headers). `Egress.routes({ plans, account })` is a route handler for the sign-in API. `examples/vercel` is one Node function (`api/index.ts`, every path rewritten to it; the Web `Request` keeps the original URL) with the routes and the same `/probe` and `/probe-socket` routes behind `DEMO_TOKEN`, calling the plan's `dispatch` and `socket.open` as nanocode-ts does. Its `.npmrc` sets `install-links`, because Vercel's file tracing leaves out a symlinked `file:../..` dependency and the function then deploys without `nanocode-egress`. To deploy it: `vercel link`, `vercel integration add upstash/upstash-kv` (which sets `KV_REST_API_URL` and `KV_REST_API_TOKEN`; it also writes Upstash agent skills into the directory, which the repository does not keep), `vercel env add PLAN_SECRET` and `DEMO_TOKEN` as sensitive production variables, then `vercel build --prod` and `vercel deploy --prebuilt --prod`.

## Status

Checked on 2026-10-28 with the tests above and nanocode-ts#167's `src/vercel/Harness.test.ts`, where the real WASM runtime sent a signed-in account's requests to `https://api.anthropic.com/v1/messages?beta=true` through the plan's dispatch. The same day `examples/cloudflare` under `wrangler dev`, with the relay on the same Mac, signed a real ChatGPT account in through the device code (its Durable Object records were sealed `v1.` envelopes, with no device code or token in plaintext), and `/probe` and `/probe-socket` got `response.completed` from gpt-6-luna over HTTPS and WebSocket through the relay; without the relay both got 403. The Claude routes answered with a real authorization URL and refused a wrong code with `Claude.InvalidError`. Deployed the same day (the Worker on Tempo Development Resources with the relay in a `lite` container, the Vercel function on tempoxyz with a pay-as-you-go Upstash database in iad1), both refused requests without the token with 401, a real ChatGPT account signed in on each through the device code, and gpt-6-luna answered `pong` with `response.completed` on all four paths: the Worker over HTTPS through the container in 4.4 s (the container's cold start included) and over WebSocket in 2.2 s, and Vercel direct, without a relay, over HTTPS in 2.3 s and over undici's WebSocket in 2.2 s. A real Claude account then signed in on both through the pasted code, and claude-haiku-5-5 (Claude Code's system prompt, `stream: true`) answered `pong` with `end_turn` directly from the Worker in 1.1-1.3 s and, after the `content-encoding` fix above, from the Vercel function in 1.1 s; all six paths passed again after redeploying both. Then real nanocode agents ran on both plans, each turn asked to compute 1234 × 5678 in a Code Mode cell: on the Worker through `/sessions/<name>/turns`, Claude (claude-haiku-5-5, direct) completed in 2.0 s of run time and ChatGPT (gpt-6-luna, its WebSocket through the container) in 6.1 s, each with an `exec` of `text(1234 * 5678)` and the answer `7006652`; on Vercel, from a scratch copy of `examples/vercel` with an `/agent` route that ran `durableSessions({ harness: Harness.create({ codeMode: true, subscription, dispatch, workspace: false }) })` from gakonst/nanocode-ts#167 (packed locally, since no release has it) on the local Workflow world in `/tmp`, with a `dispatch` that refused everything so only the plan could answer, Claude took 3.5 s and ChatGPT 5.0 s with the same cell and answer. `Harness.create` then left Code Mode off unless `codeMode: true`, and without it gpt-6-luna called `web__run` directly, which failed (not investigated); since gakonst/nanocode-ts#168 (`build-6cbf34b`) every nanocode-ts session is Code Mode only, with `exec` and `wait` as the model's only tools. `examples/vercel` has no agent route, because a Vercel agent needs durable-harness's flow route and a Workflow world, which a Next app wraps with `withDurableHarness` as gakonst/nanocode-vercel-durable does; the scratch route ran on the local world in `/tmp`, which lasts one Function instance. After the test the plans were signed out and both deployments and the Upstash database deleted. A Worker cannot reach chatgpt.com without a container: its `fetch` always carries `cf-worker`, and a deployed Worker's `connect()` to chatgpt.com or api.anthropic.com failed with "proxy request failed, cannot connect to the specified address" (Cloudflare refuses sockets to addresses it serves), while the same socket to api.github.com returned 200. Whether a third-party deployment may sign users in with their consumer plans is up to Anthropic's and OpenAI's terms; check them before a public demo serves it.

`prototypes/` holds the code this started from, recovered from gakonst/nanocode's history: `examples/cloudflare-egress` at ef31ecf7d~1 (a broker Worker behind a Service Binding with a singleton Codex OAuth Durable Object and placeholder replacement, after iron-proxy), `js/account/worker`'s subscription auth, credential vault and ChatGPT egress at 2d4a4c539~1, and `examples/cloudflare-workers`' subscription egress scripts at bb476038f and 65e92da38.

Every push to main runs `.github/workflows/release.yml`: `npm ci` (whose `prepare` builds `dist`), the type checks and tests, and a GitHub release `build-<sha>` with `nanocode-egress-<sha>.tgz`, the packed package with `dist` built, which installs without a build step, as nanocode-ts's `build-<sha>` releases do.
